📐 공통 통신 규약

모든 화면이 공유하는 기본 규약. 각 화면 명세 전 반드시 적용.

Base URL · 헤더

// 모든 요청 공통
Base URL : http://api.{domain}/v1
인증 헤더 : Authorization: Bearer {access_token}
Content-Type : application/json; charset=utf-8
Accept-Language : ko-KR
인증 불필요 API · POST /auth/signup, POST /auth/login, POST /auth/refresh, GET /auth/check-email — 그 외 모두 Authorization 필수.

공통 응답 포맷

성공

{
  "status": "success",
  "data": { ... },
  "message": "요청이 성공적으로 처리되었습니다"
}

실패

{
  "status": "error",
  "error": {
    "code": "AUTH_INVALID",
    "message": "이메일 또는 비밀번호가 일치하지 않습니다"
  }
}

공통 에러 코드

HTTPcode처리 가이드
400INVALID_PARAM인라인 필드 에러 표시
401AUTH_EXPIRED/auth/refresh 자동 호출 → 원 요청 1회 재시도
401AUTH_INVALID토큰 폐기 → W-02로 강제 이동
403FORBIDDEN토스트 "권한이 없습니다"
404NOT_FOUND화면별 빈 상태 처리
409DUPLICATE인라인 에러 (예: 이메일 중복)
429RATE_LIMIT토스트 "잠시 후 다시 시도해주세요"
500INTERNAL_ERROR토스트 + Sentry 보고

토큰 라이프사이클

[401 AUTH_EXPIRED 감지] → POST /auth/refresh (refresh_token) ├ 200 → access_token 갱신 + 원 요청 재시도(1회만) └ 401 → 토큰 모두 삭제 → W-02 이동

날짜 · 페이지네이션 규약

  • 날짜/시간 : ISO 8601 UTC (2026-05-13T10:00:00Z)
  • 페이지네이션 : ?page=1&size=20 · 응답에 pagination 객체 포함

W-02🔐 로그인

이메일 / 비밀번호 입력 → 토큰 발급 + FCM 등록 → W-04 이동.

호출 API

POST/auth/login · "로그인" 버튼
POST/notifications/fcm-token · 로그인 성공 후 백그라운드

1. POST /auth/login

Request Body

{
  "email": "user@example.com",
  "password": "abcd1234!"
}

Response 200

{
  "status": "success",
  "data": {
    "access_token": "eyJhbGc...",
    "refresh_token": "dGhpcyBpcy...",
    "token_type": "Bearer",
    "expires_in": 3600,
    "user": {
      "id": 1,
      "email": "user@example.com",
      "nickname": "투자자_a3k9"
    }
  }
}

Error

상황HTTPcodeUI
비밀번호 불일치401AUTH_INVALID인라인: "이메일 또는 비밀번호가 일치하지 않습니다"
형식 오류400INVALID_PARAM필드별 인라인
네트워크 실패——토스트: "네트워크 연결을 확인해주세요"

2. POST /notifications/fcm-token

Request Body

{
  "device_token": "fcm-device-token-string",
  "platform": "ios"
}

Response 200

{ "status": "success", "message": "디바이스 토큰이 등록되었습니다" }

프론트 처리 흐름

[로그인 버튼] → POST /auth/login ├ 200 → access_token + refresh_token 보안 저장 (Keychain / EncryptedSharedPreferences) │ → FCM SDK에서 device_token 조회 │ → POST /notifications/fcm-token (백그라운드 · 실패해도 진행) │ → W-04로 이동 └ 401 → 인라인 에러 표시

W-03📝 회원가입

이메일 중복 체크 → 비밀번호/약관 검증 → 가입 완료 → W-02로 복귀.

호출 API

GET/auth/check-email · 이메일 blur (debounce 500ms)
POST/auth/signup · "가입하기" 버튼

1. GET /auth/check-email

Request

GET /auth/check-email?email=user@example.com

Response — 사용 가능

{ "status": "success", "data": { "available": true } }

Response — 이미 가입

{
  "status": "success",
  "data": { "available": false, "message": "이미 가입된 이메일입니다" }
}

2. POST /auth/signup

Request Body

{
  "email": "user@example.com",
  "password": "abcd1234!",
  "nickname": "투자자_홍길동",          // optional · 미입력 시 서버 자동 생성
  "terms_agreed": true,
  "privacy_agreed": true,
  "marketing_agreed": false
}

Response 201

{
  "status": "success",
  "data": {
    "user_id": 1,
    "email": "user@example.com",
    "nickname": "투자자_a3k9",
    "created_at": "2026-05-13T10:00:00Z"
  },
  "message": "회원가입이 완료되었습니다"
}

Error

상황HTTPcodeUI
이메일 형식 오류400INVALID_PARAM field=email인라인
비밀번호 규칙 (영문+숫자 8자↑)400INVALID_PARAM field=password인라인
비밀번호 확인 불일치—클라이언트 검증인라인
이메일 중복409DUPLICATE"이미 가입된 이메일입니다"
필수 약관 미동의—클라이언트 검증가입 버튼 비활성화

프론트 처리 흐름

[이메일 입력 → blur] → debounce 500ms → GET /auth/check-email?email= ├ available:true → ✓ 사용가능 (초록) └ available:false → ✗ 이미 가입됨 (빨강) [가입 버튼] → 클라이언트 검증 (비밀번호 강도 · 일치 · 약관) → POST /auth/signup ├ 201 → 토스트 "가입 완료" → W-02로 이동 (자동 로그인 X) └ 4xx → 에러 매핑
